# Hilos v2 - Техническое задание

## Обзор проекта
Hilos v2 - это высоконагруженный фреймворк для создания кластерных систем с лёгким демоном и распределённой обработкой задач.

## Архитектурные принципы

### Основная концепция
- **Лёгкий демон** - минимальное потребление ресурсов, только управление
- **Кластерная архитектура** - несколько серверов объединяются в кластер
- **Дочерние процессы** - вся тяжёлая работа выносится в отдельные процессы/workers
- **5 типов сокетов** - специализированные каналы связи
- **Event-driven архитектура** - асинхронная обработка через main loop
- **Graceful shutdown и hot reloading** - корректное завершение и обновление без остановки

### Архитектурные решения
- **НЕ микросервисная** - монолитная архитектура с распределёнными компонентами
- **НЕ plugin-based** - всё встроено в фреймворк
- **Main loop с socket_select** - единый цикл обработки всех сокетов
- **Non-blocking sockets** - все операции неблокирующие с delay write/read

### Компоненты системы

#### 1. Daemon Core
- Минимальный демон-менеджер
- Управление жизненным циклом процессов
- Кластерное управление
- Graceful shutdown
- **Server и Client классы** - для всех 4 типов сокетов
- **Обработка сокет ошибок** - все возможные ошибки сокетов
- **WebSocket протоколы** - классы реализации разных протоколов
- **Worker классы** - абстрактные worker со стороны daemon и worker
- **Agent классы** - заготовки для агентов с обеих сторон

#### 2. Socket Architecture (5 типов)
1. **WebSocket** - для общения с дочерними процессами (поддержка разных протоколов)
2. **CLI/Internal Signals** - для управления через командную строку и внутренних сигналов (HTTP/HTTP2 запросы в daemon)
3. **HTTP** - стандартный HTTP/HTTP2 сервер
4. **Swarm (Cluster)** - для связи между daemon'ами в кластере
5. **Worker Communication** - для общения с worker процессами

**Протокол связи**: JSON обёрнутый в DTO через неблокирующие сокеты с поддержкой сжатия контента между серверами кластера

#### 3. Process Management
- **Workers** - основные рабочие процессы (через proc_open)
- **Agents** - классы с методом tick(), вызываемым каждые 0.1 секунды
- **Task Processes** - отдельные процессы для конкретных задач (через proc_open)
- **AI Services** - специализированные сервисы для работы с GPU

#### 4. Agent Types (по конфигурации)
- **Monopolistic Agents** - требуют монопольного worker
- **High Frequency Agents** - лёгкие, но требуют высокой частоты (один поток)
- **Blocking Agents** - могут подвисать на N секунд (не более M процессов в worker)
- **Resource-specific Agents** - требуют специфических ресурсов окружения (GPU, память, CPU), настраиваемых в конфигурации

## Функциональные требования

### Кластерное управление
- [ ] **Master-Slave архитектура** - Master содержит полную конфигурацию кластера, Slave знают только адрес Master
- [ ] **TCP сокеты для синхронизации** - прямые TCP соединения между нодами
- [ ] **Heartbeat система** - регулярные ping/pong между Master и Slave, между Master и Workers
- [ ] **Hot reloading с уведомлением** - обновление в фоне с сигналом "режим обслуживания"
- [ ] **Режим обслуживания** - nginx перенаправляет на простой сервер при недоступности master daemon
- [ ] **Процесс перезагрузки** - остановка агентов, завершение WebSocket соединений, обновление, перезапуск
- [ ] **Graceful shutdown** - WebSocket остается активным до последнего, отправка сигнала о перезагрузке
- [ ] **TLS для межсерверного общения** - с возможностью отключения для отдельных маршрутов
- [ ] **Управление сертификатами** - один сертификат с ежегодным обновлением
- [ ] **Конфигурация TLS** - настройка TLS по маршрутам в конфигурации
- [ ] **Внутренний мониторинг** - метрики только для внутреннего использования
- [ ] **Zabbix интеграция** - отправка метрик в Zabbix
- [ ] **Алерты при падениях** - уведомления о сбоях
- [ ] **Сигнал-роутер** - маршрутизация сигналов между агентами с поддержкой приоритетов
- [ ] **Типы сигналов** - session, subscribe, subscribe-group, action
- [ ] **Маршруты сигналов** - user->master, user->agent, master->worker, master->agent, master->user, worker->agent, worker->master, worker->worker, agent->master, agent->user, agent->worker
- [ ] **Автозапуск агентов** - автоматический запуск недоступных агентов для доставки сигналов
- [ ] **Приоритеты сигналов** - система приоритетов для упорядочивания обработки сигналов

## Детальные объяснения

### API протоколы

#### REST API
- **GET /api/users** - получить список пользователей
- **POST /api/users** - создать пользователя
- **PUT /api/users/1** - обновить пользователя
- **DELETE /api/users/1** - удалить пользователя
- **PATCH /api/users/1/lock** - заблокировать пользователя для безопасных операций
- **PATCH /api/users/1/unlock** - разблокировать пользователя
- Стандартные HTTP методы и коды ответов

#### JSON-RPC
- Вызовы методов через JSON
- Поддержка batch запросов
- Уведомления (без id)

### Middleware/Filters система

#### Middleware (промежуточная обработка)
- Аутентификация - проверка прав доступа
- Логирование - запись запросов и ответов
- CORS - обработка кросс-доменных запросов
- Валидация - проверка входных данных

#### Pre/Post Handlers
- Pre-handler - обработка до основного обработчика (валидация, подготовка данных)
- Post-handler - обработка после основного обработчика (форматирование ответа, кеширование)

### Встроенный JSON API
- **Автоматическая генерация** API из Entity классов
- **CRUD операции** для всех сущностей
- **Фильтрация и пагинация** из коробки
- **Валидация** на основе Entity правил
- **Документация** API автоматически генерируется

## Точки входа и запуск

### Основные точки входа
- **`cli`** - единый CLI интерфейс для управления daemon и worker процессов (executable файл без расширения)

### Примеры запуска
```bash
# Запуск daemon
./cli daemon:start

# Управление через CLI
./cli status
./cli daemon:restart
./cli monitor

# Запуск worker (внутренняя команда, вызывается daemon'ом)
./cli worker:start --worker-id=1
```

### Как это работает
- **CLI файл** - исполняемый файл без расширения с shebang `#!/usr/bin/env php`
- **Bootstrap классы** - CliBootstrap, DaemonBootstrap, WorkerBootstrap в framework/src/Bootstrap/
- **Команды** - все команды (daemon:start, worker:start, status, etc.) обрабатываются через единый CLI интерфейс
- **Unix совместимость** - файл cli работает во всех Unix-подобных системах (Linux, macOS, BSD)

## Поддерживаемые протоколы

### WebSocket протоколы
- **Стандартный WebSocket** - базовый протокол RFC 6455
- **WAMP (WebSocket Application Messaging Protocol)** - для RPC и Pub/Sub
- **JSON-RPC over WebSocket** - для удалённых вызовов процедур
- **Кастомные протоколы** - если нужны специфические требования
- **WebSocket для таблиц** - стандартный WebSocket с определённым форматом сообщений для работы с большими таблицами

### Socket типы
1. **WebSocket** - общение с дочерними процессами (поддержка разных протоколов)
2. **CLI/Internal Signals** - управление через командную строку и внутренние сигналы (HTTP запросы в daemon)
3. **HTTP** - стандартный HTTP сервер
4. **Swarm (Cluster)** - связь между daemon'ами в кластере
5. **Worker Communication** - общение с worker процессами

### Протокол связи
- **JSON в DTO** - все данные обёрнуты в DTO и сериализованы в JSON
- **Non-blocking sockets** - все операции неблокирующие с delay write/read
- **Socket error handling** - обработка всех возможных ошибок сокетов

## Требования к базе данных

### ORM
- [ ] **Самодельная ORM** - собственная реализация
- [ ] **Миграции** - самодельная система миграций
- [ ] **Entity и CollectionEntity** - сущности таблиц БД и их коллекции
- [ ] **Tuple и CollectionTuple** - для кастомных SQL запросов без привязки к таблицам
- [ ] **mysqli только** - работа исключительно с mysqli
- [ ] **Адаптеры на будущее** - заложить возможность других драйверов
- [ ] **Множество Exception** - 8 connection + 12 runtime + 3 абстрактных + 1 самодельная
- [ ] **Хранимые процедуры** - вызов хранимок, функций, множественные result set
