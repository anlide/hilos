# Варианты: приём entities во framework, типы и хранилище из проекта

> Примечание: это исторический документ про generic `entities` channel.
> Текущая политика для browser-facing DB/RT состояния — использовать
> BrowserContext rows для page-shaped payloads или `frontend.full` /
> `frontend.updates` и typed frontend projections для project-wide collections.
> Например, публичные `users` больше не должны приходить через
> `entities.full.users`.

## Исходные условия

1. **Любой ответ, содержащий `entities`**, запускает один общий парсер. Код этого процесса живёт во **framework**; **типы данных** (User, Event и т.д.) и правила конвертации — в **конкретном проекте**.

2. **Подход как в pet-проекте:** в хранилище подаётся кусок payload **неизвестного типа**; хранилище либо преобразует его в свои объекты (штатный случай), либо не может — и тогда исключение. Хочется то же здесь, **с наследованием, если это возможно** в TypeScript/Vue.

3. Ниже варианты уже с учётом этого. В конце — про наследование в TS/Vue и почему «хранилище как класс с наследованием» возможно не в виде самого Pinia-store.

---

## Общее для всех вариантов

- **Framework** знает только конверт: у сообщения может быть `data.entities` — объект с опциональными полями `full`, `updates`, `deleted`. Каждое поле — объект «ключ коллекции → массив» (`full`/`updates` — массивы элементов, `deleted` — массив id). Framework извлекает этот конверт и **запускает процесс расфасовки**, не зная про users/events и типы.
- **Проект** задаёт: для каких ключей коллекций что делать, как из `unknown[]` сделать типизированные сущности и куда их положить (в своё хранилище).

---

## Вариант 1: Базовый класс «приёмщик entities» в framework (наследование)

**Идея:** В framework живёт класс, который принимает сырой payload и руководит процессом. Конвертация и применение — в методах, которые проект переопределяет. Типы — только в проекте.

**Framework:**

- Класс, например `EntitiesReceiver`:
  - Метод `apply(payload: unknown): void`:
    - Проверяет, что payload — объект с полем `entities` (объект). Если нет — выходит или бросает.
    - Достаёт `full`, `updates`, `deleted` (как `Record<string, unknown[]>` и `Record<string, number[]>`).
    - Для каждого ключа в `full`: вызывает `applyFull(collectionKey: string, rawItems: unknown[]): void`.
    - Для каждого ключа в `updates`: вызывает `applyUpdates(collectionKey: string, rawItems: unknown[]): void`.
    - Для каждого ключа в `deleted`: вызывает `applyDeleted(collectionKey: string, ids: number[]): void`.
  - Методы по умолчанию (можно пустые или с логированием):  
    `applyFull(key, raw)`, `applyUpdates(key, raw)`, `applyDeleted(key, ids)`.  
    В проекте их переопределяют.

**Проект:**

- Класс, например `ChatEntitiesReceiver extends EntitiesReceiver`:
  - В `applyFull(key, rawItems)` при `key === 'users'` парсит `rawItems` в массив (валидация, при ошибке — throw), создаёт `User.fromObject(...)` и вызывает свой store (или внутреннее состояние) — `upsertUsers(...)`. Для `key === 'events'` — то же с Event и `clearEvents` + `addEvent`. Остальные ключи — игнор или throw.
  - Аналогично `applyUpdates` и `applyDeleted` для `users` и `events`.
- При создании плагина создаётся экземпляр `new ChatEntitiesReceiver(chatStore)` (или store передаётся в методах). В `onMessage` при получении сообщения: если у `data` есть `entities`, вызывается `receiver.apply(data)`.

**Типы:** только в проекте (User, Event, типы полей). Framework оперирует только `unknown[]` и `number[]`.

**Наследование:** да. Базовый класс во framework задаёт процесс; проект наследует и подставляет свою конвертацию и применение. «Подали payload неизвестного типа → приёмщик либо преобразует через свои методы, либо бросает» — это и есть этот класс.

## Вариант 2: Тот же приёмщик, но «хранилище» передаётся снаружи

То же, что вариант 1, но базовый класс не хранит ссылку на store, а получает её в конструкторе или в каждом `apply`: например `apply(payload: unknown, store: unknown): void`, и при вызове `applyFull(key, raw)` framework только вызывает переопределённый метод, а проект внутри себя вызывает `store.upsertUsers(...)`. Так «хранилищем» остаётся Pinia-store проекта; приёмщик — отдельный класс, который умеет в него раскладывать. Наследование по-прежнему: базовый класс во framework, в проекте — наследник с типизированной конвертацией и обращением к своему store.

## Вариант 3: Базовый класс «хранилище с приёмом entities»

**Идея:** Не отдельный «приёмщик», а базовый класс хранилища, у которого есть метод «принять кусок payload неизвестного типа и разложить по себе». Как в твоём pet-проекте: хранилище само умеет из payload сделать объекты и положить в себя, иначе — исключение.

**Особенность Vue/Pinia:** Обычный store в Pinia — это не класс, а объект из `defineStore()`. Наследование от класса и при этом использование Pinia (реактивность, devtools) «из коробки» не предполагается. Поэтому возможны два подхода:

**3a) Отдельный класс «EntitySyncStore» в framework**

- Framework: класс с методом `applyEntitiesPayload(payload: unknown): void` (как в варианте 1 — извлекает конверт и вызывает `applyFull`/`applyUpdates`/`applyDeleted` по ключам). Методы абстрактные или с дефолтной реализацией.
- Проект: класс `ChatEntitySyncStore extends EntitySyncStore` и реализует эти методы (парсинг + вызов реального store). В приложении создаётся один экземпляр `ChatEntitySyncStore`, ему при создании передаётся Pinia-store (или его actions). При приходе сообщения с `entities` вызывается `syncStore.applyEntitiesPayload(data.entities)`.
- «Хранилище» в твоей формулировке — это по смыслу именно этот класс: ему подают payload неизвестного типа, он конвертирует и прокидывает в настоящее хранилище (Pinia). Наследование — от базового класса framework.

**3b) Pinia-store вызывает framework, а не наследует**

- Framework экспортирует функцию `applyEntitiesEnvelope(envelope, handlers)`: извлекает конверт из payload и для каждого ключа вызывает соответствующие функции из `handlers[key]`.
- В проекте Pinia-store имеет action, например `applyEntitiesPayload(payload: unknown)`: внутри вызывает framework’овскую функцию, передавая объект handlers, где для `users`/`events` указаны функции, которые парсят `unknown[]` и вызывают `this.upsertUsers` / `this.addEvent` и т.д. При невалидных данных парсеры бросают — получается «подали в store кусок payload → store либо преобразовал, либо исключение».
- Наследования класса store тут нет: «хранилище» — по-прежнему Pinia-store, а framework даёт только процесс (функцию) и контракт handlers.

## Вариант 4: Любой ответ с `entities` обрабатывается во framework без явного типа сообщения

**Идея:** В WebSocket-слое (framework) при получении любого сообщения проверяем: есть ли у него `entities`. Если есть — не смотрим на `type` сообщения, сразу запускаем общий парсер и расфасовку. Типы и правила — из проекта (через приёмщик или handlers).

**Framework:**

- При создании плагина можно передать, например, `entitiesReceiver: EntitiesReceiver` (вариант 1) или `onEntities: (payload: unknown) => void`.
- В обработчике сообщений (внутри framework или в одном общем колбэке, который framework вызывает):  
  `if (data && typeof data === 'object' && 'entities' in data && data.entities != null) { entitiesReceiver.apply(data); }`  
  Затем вызывается пользовательский `onMessage(data)` (или следующий шаг pipeline), чтобы проект мог отреагировать на тип сообщения (handshake_response, subscription_page_main и т.д.).

**Проект:**

- Реализует приёмщик (наследник или объект с методами) и передаёт его в опции плагина. В `onMessage` проект обрабатывает только «смысл» сообщения (userId, тип события), не парсинг entities — он уже выполнен.

Итог: «любой ответ с entities запускает общий парсер» — да, это делает framework; данные расфасовываются в проектное хранилище через приёмщик с проектными типами.

## Вариант 5: Типы данных «из проекта» через регистрацию коллекций

**Идея:** Framework не только извлекает конверт, но и даёт способ зарегистрировать «для ключа X — как парсить и куда применять». Типы при этом остаются в проекте: парсер возвращает `unknown` или generic, проект при регистрации передаёт функции, работающие со своими типами.

**Framework:**

- Тип конверта: `EntitiesEnvelope = { full?: Record<string, unknown[]>, updates?: ..., deleted?: Record<string, number[]> }`.
- Функция или класс, например `createEntitiesReceiver()`: принимает объект регистрации вида  
  `{ [collectionKey: string]: { parseItem?(raw: unknown): unknown; applyFull(items: unknown[]): void; applyUpdates?(items: unknown[]): void; applyDeleted?(ids: number[]): void } }`.  
  Для `full` и `updates` по каждому ключу вызывается parseItem для каждого элемента (или проект сам получает массив и парсит целиком), затем applyFull/applyUpdates. Для deleted — applyDeleted.
- При `apply(payload)` framework извлекает конверт и для каждого ключа вызывает зарегистрированные методы. Если для ключа нет регистрации — пропуск или опция «throw».

**Проект:**

- Регистрирует для `users`: parseItem (или один парсер на массив) → проверка + `User.fromObject`, applyFull/applyUpdates → вызов store.upsertUsers, applyDeleted → store.removeUsers. Аналогично для `events`. Типы User, Event и форма payload — только в проекте.

Наследования класса тут нет: «управление процессом» во framework, «типы и конвертация» инжектятся через регистрацию. Если нужно именно наследование — комбинируется с вариантом 1: базовый класс в framework принимает в `apply` payload и вызывает абстрактные applyFull/applyUpdates/applyDeleted; проект наследует этот класс и в реализациях использует свои типы и store.

---

## Про наследование в TypeScript/Vue в этом контексте

- **Наследование как «базовый класс процесса, проект подставляет типы и применение»** — возможно и нормально: в framework — абстрактный или с дефолтной реализацией класс (например, `EntitiesReceiver`); в проекте — класс `ChatEntitiesReceiver extends EntitiesReceiver` с реализацией `applyFull`/`applyUpdates`/`applyDeleted`, где используются User, Event и вызовы store. Это и есть твой вариант «подали неизвестный payload → что-то его преобразует в объекты или бросает», при этом процесс общий (framework), типы и хранилище — из проекта.

- **Наследование именно Pinia-store от класса framework** — так в Vue/Pinia обычно не делают: store создаётся через `defineStore()`, это не класс. Поэтому «хранилище, которое принимает payload» лучше оформить как отдельный класс (приёмщик / EntitySyncStore), который при создании получает ссылку на реальный Pinia-store и при `apply(payload)` раскладывает данные в него. Тогда «наследование» есть у этого приёмщика, а не у самого store.

- **Итог:** твою схему («любой ответ с entities → общий парсер; типы из проекта; хранилище принимает кусок неизвестного типа и конвертирует или бросает») можно реализовать с наследованием: базовый класс во framework задаёт процесс приёма и вызов абстрактных/переопределяемых методов; в проекте — наследник с типизированной конвертацией и обращением к своему (например, Pinia) хранилищу. Отдельный класс-приёмщик наследуется от базового; само хранилище (Pinia) остаётся отдельным объектом, в который приёмщик пишет.

## Краткая сводка вариантов

| Вариант | Где процесс | Типы / конвертация | «Хранилище принимает unknown» | Наследование |
|--------|------------|--------------------|-------------------------------|--------------|
| 1 | Framework (базовый класс) | Проект (переопределение методов) | Класс-приёмщик | Да, приёмщик наследует базовый класс |
| 2 | Как 1, store передаётся снаружи | Как 1 | Как 1 | Да |
| 3a | Framework (EntitySyncStore) | Проект (наследник) | Класс sync store | Да, sync store наследует базовый |
| 3b | Framework (функция applyEnvelope) | Проект (handlers в store) | Store action вызывает framework | Нет наследования store |
| 4 | Framework при любом сообщении с entities | Проект (приёмщик) | Как 1/2 | По желанию (как 1) |
| 5 | Framework (регистрация по ключам) | Проект (при регистрации) | Через callbacks | Нет, можно комбинировать с 1 |

Рекомендация для «как в pet-проекте + наследование»: **вариант 1 или 3a** — базовый класс во framework, в проекте наследник с типизированной конвертацией и записью в своё хранилище; при любом сообщении с `entities` (вариант 4) framework вызывает `receiver.apply(data)`.
